FortiGate CLI Grundlagen — und eine Splunk-Lizenzverletzung zurückverfolgt

Begonnen als reine CLI-Übung auf einer FortiGate-VM: die fünf Grundbefehle, die Config-Navigation, ein read-only Rundgang durch Interfaces, Routing und Policies. Am Ende erklärte genau dieser Rundgang einen ganz anderen Fehler von früher am Tag — warum Splunk plötzlich keine Suchen mehr zuließ.

FortiOS CLI get / show / config Firewall Policy Syslog Forwarding Splunk Lizenz Log-Volumen
5 CLI-Grundbefehle: get / show / config / execute / diagnose
5514/udp Syslog-Port, über den die Logs liefen
logtraffic all Die Policy-Einstellung, die die Lizenz sprengte

Fünf Verben, eine Grammatik

Fast alles in der FortiOS-CLI reduziert sich auf einen von fünf Befehlen. Sobald man weiß, wofür jeder einzelne gedacht ist, hört unbekannte Ausgabe auf, einschüchternd zu sein.

get

Liest den laufenden Zustand — was die Box gerade tatsächlich tut. get system status

show

Liest die gespeicherte Konfiguration, im Config-Script-Format. show firewall policy

config

Betritt einen Config-Kontext, um Einstellungen zu ändern. config system interface

execute

Führt eine einmalige Aktion aus — keine Einstellung. execute ping 8.8.8.8

diagnose

Low-Level-Troubleshooting, nah am Kernel. diagnose sys top

Die eine Regel, über die jeder Neuling stolpert

execute, get und diagnose funktionieren nur auf der Root-Ebene. Sobald man einen config-Block betritt, ändert sich die Grammatik — edit, next, end, abort übernehmen, bis man wieder rausklettert.

FGVMEVIJFXCOFND1 # config system interface │ FGVMEVIJFXCOFND1 (interface) # edit "port1" │ FGVMEVIJFXCOFND1 (port1) # set ip 192.168.1.1 255.255.255.0 │ FGVMEVIJFXCOFND1 (port1) # next → Objekt speichern, zurück zur Tabelle FGVMEVIJFXCOFND1 (interface) # end → alles speichern, zurück zur Root-Ebene │ FGVMEVIJFXCOFND1 #
⚠️

Typischer Fehler: execute ping 8.8.8.8 innerhalb von (interface) # eingeben — command parse error. Kein kaputtes Gerät, nur die falsche Grammatik für die aktuelle Ebene. Erst end oder abort, dann funktioniert execute wieder.

Durch die Box: ein read-only Rundgang

Ein reiner Lesedurchgang über eine FortiGate-ARM64-KVM-VM — Version, Interfaces, Nachbarn, Routing, Policy — ausschließlich mit get, show und diagnose.

GET SYSTEM STATUS Identität und Lizenzstatus der VM
FGVMEVIJFXCOFND1 # get system status # Version, Lizenz, HA-Modus — der Ausweis der Box Version: FortiGate-ARM64-KVM v7.4.12,build2902,260505 (GA.M) License Status: Valid VM Resources: 1 CPU/1 allowed, 1990 MB RAM/2048 MB allowed Operation Mode: NAT Current HA mode: standalone

Eine virtuelle FortiGate unter KVM, standalone, im gerouteten/NAT-Modus, auf Lab-Größe zugeschnitten (1 vCPU / 2 GB Cap). Signaturdatenbanken aus 2015–2018 sind bei einer Offline-Eval-Box normal — kein Fehler.

GET SYSTEM INTERFACE PHYSICAL Live-Zustand statt gespeicherter Config
FGVMEVIJFXCOFND1 # get system interface physical ==[port1] mode: dhcp ip: 192.168.64.2/24 status: up ==[port2] mode: static ip: 10.66.66.1/24 status: up ==[port3] mode: static ip: 192.168.1.99/24 status: up

show system interface zeigt, was konfiguriert wurde; get … physical zeigt, was gerade tatsächlich läuft. Port1 ist der DHCP-WAN-Uplink, Port2 und Port3 sind statische interne Lab-Segmente.

GET ROUTER INFO ROUTING-TABLE ALL Cisco-Style Route-Codes statt Kernel-Rohdaten
FGVMEVIJFXCOFND1 # get router info routing-table all S* 0.0.0.0/0 [5/0] via 192.168.64.1, port1 S 10.0.0.0/8 [10/0] via 192.168.64.1, port1 C 10.66.66.0/24 is directly connected, port2 C 192.168.1.0/24 is directly connected, port3 C 192.168.64.0/24 is directly connected, port1

S* markiert die Default-Route, die tatsächlich greift, wenn nichts Spezifischeres passt. C-Routen entstehen automatisch, weil ein Interface diese Adresse trägt. Die breite 10.0.0.0/8-Route fängt nur Adressen ab, die nicht schon von den spezifischeren /24-Netzen abgedeckt sind — Longest-Prefix-Match wie bei jedem Router.

SHOW FIREWALL POLICY Drei Regeln, zwei sehr unterschiedliche Sicherheitshaltungen
edit 1 "LAN-to-WAN" port3 → port1 ALL nat, av, ips, logtraffic all edit 2 "Management-HTTPS" port1 → port1 HTTPS — edit 3 "Test-Policy" port2 → port1 ALL nat, keine Profile

Policy 1 schickt den Traffic von Port3 vollständig inspiziert und vollständig geloggt ins Internet; Policy 3 macht dasselbe für Port2 — ganz ohne Security-Profile. Policy 2s port1 → port1-Paarung ist kein durchlaufender Traffic, sondern regelt den Zugriff auf die Box selbst über ihr WAN-Interface.

Die Spur: warum Splunk keine Suche mehr zuließ

Die Session begann als CLI-Übung ohne Bezug zu irgendetwas anderem. Am Ende erklärte sie einen Splunk-Fehler von früher am selben Tag.

⛔

Symptom: Error in 'litsearch' command: Your Splunk license expired or you have exceeded your license limit too many times.

1
SESSION-LISTE
Ein ruhiger, aber ununterbrochener Traffic-Flow
get system session list zeigt eine UDP-Session von der FortiGate zu 192.168.64.1:5514 — dem Mac Mini Host, auf dem klassischen Syslog-Port.
2
BESTÄTIGUNG
Der Forwarder, live nachgelesen
SHOW LOG SYSLOGD SETTING
config log syslogd setting set status enable set server "192.168.64.1" set port 5514 end
Die FortiGate streamt ihre Logs kontinuierlich auf denselben Host, auf dem Splunk läuft — über Splunks Syslog-Input-Port.
3
URSACHE
Die Verbindung zu Policy 1
Policy 1 (LAN-to-WAN) läuft mit logtraffic all — nicht nur Security-Events, sondern jede einzelne Session. Jede DNS-Anfrage, jeder Ping, jede Management-HTTPS-Session: alles, kontinuierlich, ins tägliche Ingest-Kontingent von Splunk. Über Tage hinweg im Dauerbetrieb genau die Art von Hintergrundvolumen, die Lizenzverletzungen anhäuft.
4
FIX
Den Hahn zudrehen — und nachprüfen, nicht vertrauen
CONFIG LOG SYSLOGD SETTING
FGVMEVIJFXCOFND1 # config log syslogd setting (setting) # set status disable (setting) # end FGVMEVIJFXCOFND1 # show log syslogd setting config log syslogd setting end
Keine set status enable-Zeile mehr — Forwarding ist aus, bestätigt durch erneutes Auslesen der Config statt durch bloßes Vertrauen auf den Befehl, der sie geändert hat.

Was ich gelernt habe

Prompt = Grammatik

Der Prompt zeigt die aktuelle Ebene. FGVM… # erlaubt execute/diagnose; (interface) # erlaubt nur edit/next/end.

get ≠ show

show liest die gespeicherte Absicht, get liest den tatsächlichen Live-Zustand. Beide Blickwinkel zu kennen erklärt Diskrepanzen sofort.

logtraffic all ist teuer

Volles Session-Logging auf einer Policy zählt gegen jedes nachgelagerte SIEM-Lizenzkontingent — auch für uninteressanten Traffic wie DNS-Lookups und Pings.

Nach dem Fix nachlesen

set status disable im Editor zu tippen beweist nichts — erst show log syslogd setting danach bestätigt, dass es auch angekommen ist.

💡

Nächster Schritt: Syslog-Forwarding wieder aktivieren, aber gezielt — set logtraffic utm auf Policy 1, damit nur sicherheitsrelevante Events zählen, statt jeder einzelnen Session.
