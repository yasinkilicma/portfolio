IPSec Site-to-Site VPN mit StrongSwan in Docker
— Policy-based IKEv1 auf dem MacBook Air

Ein vollständig containerisiertes IPSec-VPN-Labor auf meinem MacBook Air: zwei StrongSwan-Endpunkte auf Alpine Linux, verbunden über eine verschlüsselte Site-to-Site-Strecke. IKEv1 Main Mode, AES-256-Verschlüsselung, Dead Peer Detection — alles, was später die Basis für ADVPN und SD-WAN bildet. Und das Beste: kein UTM, keine VM, nur Docker und ein Terminal.

IPSec IKEv1 StrongSwan Docker Alpine Linux Site-to-Site VPN Policy-based VPN xfrm DPD NSE4
2 StrongSwan-Endpunkte (Mannheim + Heidelberg)
< 0,5 ms Latenz über den IPSec-Tunnel
100 % Erfolgsrate Ping-Test (beide Richtungen)

Warum ein IPSec-Labor auf dem MacBook?

Für die NSE4-Vertiefung brauchte ich eine realistische Site-to-Site-VPN-Umgebung — aber mein MacBook Air hat weder Platz für mehrere UTM-VMs noch die nötige Kühlung für stundenlange Labor-Sessions. Die Lösung: zwei Docker-Container mit StrongSwan. Leichter geht's nicht. Ein Docker-Netz simuliert das Internet, zwei Loopback-Interfaces die lokalen LANs, und der Linux-Kernel erledigt die Verschlüsselung über sein xfrm-Subsystem.

Der Plan war: Policy-based IKEv1 mit Pre-Shared Keys, AES-256 und SHA-256, DPD für Verbindungsstabilität — und alles per CLI konfiguriert, wie es in deutschen Systemhäusern Standard ist.

Die Topologie

Zwei Alpine-Container teilen sich ein Docker-Bridge-Netz (10.255.0.0/24), das als öffentliches Internet dient. Jeder Container hat eine Loopback-IP, die sein internes LAN repräsentiert (10.0.1.0/24 für Mannheim, 10.0.2.0/24 für Heidelberg).

Container: Site-A (Mannheim) Container: Site-B (Heidelberg) 10.255.0.10 10.255.0.20 │ │ │ ┌──────────────────────────────────────────┐ │ │ │ IPSec Tunnel (AES-256-CBC / SHA-256) │ │ │ │ IKEv1 Main Mode, DH-2048, PSK │ │ │ └──────────────────────────────────────────┘ │ │ │ lo: 10.0.1.1/24 lo: 10.0.2.1/24 │ │ eth0 ─── internet (10.255.0.0/24) ─── eth0

Die Konfiguration — Phase für Phase

Pre-Shared Key

Beide Seiten teilen sich denselben PSK. Wichtig: die Reihenfolge der IPs im ipsec.secrets ist auf Site-A und Site-B spiegelverkehrt.

SITE-A / SITE-B ipsec.secrets — symmetrisch, aber gespiegelt
# Site-A: 10.255.0.10 10.255.0.20 : PSK "..." # Site-B: 10.255.0.20 10.255.0.10 : PSK "..." 10.255.0.10 10.255.0.20 : PSK "Mannheim-Heidelberg-2024-Gizli-Anahtar"

IKE Phase 1 (ISAKMP-SA)

Die ike=-Zeile definiert die Proposal für die IKE-SA. Proposals werden mit ! als strict markiert — StrongSwan akzeptiert dann nur diese exakte Kombination.

IPSEC.CONF Site-A (Mannheim)
conn site-to-site auto=start type=tunnel keyexchange=ikev1 authby=secret # Site-A (Mannheim) left=10.255.0.10 leftsubnet=10.0.1.0/24 leftid=@site-a.mannheim # Site-B (Heidelberg) right=10.255.0.20 rightsubnet=10.0.2.0/24 rightid=@site-b.heidelberg # Phase 1 ike=aes256-sha256-modp2048! ikelifetime=86400s # Phase 2 esp=aes256-sha256-modp2048! lifetime=3600s # DPD dpdaction=restart dpddelay=30s dpdtimeout=120s

Symmetrie beachten: Auf Site-B ist left=10.255.0.20 und right=10.255.0.10 — StrongSwan interpretiert left als lokal und right als remote.

Das Labor starten

Der Einstieg ist bewusst minimalistisch gehalten. Ein docker-compose.yml definiert beide Sites, ein Dockerfile baut das StrongSwan-Image.

BASH Projekt klonen und starten
git clone https://github.com/yasinkilicma/ipsec-vpn-lab cd ipsec-vpn-lab docker compose build docker compose up -d

Nach dem Start initialisiert StrongSwan automatisch die IKE-SA. Der gesamte Aushandlungsprozess lässt sich live im Log verfolgen:

BASH Live-Log der IKE-Aushandlung
docker logs -f ipsec-vpn-lab-site-a-1

Der IKEv1 Main Mode — 6 Messages im Detail

IKEv1 Main Mode tauscht insgesamt sechs Nachrichten aus, bevor der erste verschlüsselte Datenverkehr fließt. Die Debug-Ausgabe (charondebug="ike 2, knl 2, cfg 2") zeigt jeden Schritt.

Message 1 + 2 — SA-Vorschlag

Beide Seiten senden ihre Proposal-Liste für Verschlüsselung (AES-256), Hash (SHA-256) und DH-Gruppe (MODP-2048). StrongSwan wählt den ersten Treffer.

Message 3 + 4 — Diffie-Hellman-Key-Exchange

Jede Seite generiert einen privaten DH-Wert und sendet den öffentlichen Schlüssel plus einen Nonce. Aus den Nonces wird SKEYID abgeleitet — der Master-Schlüssel für alle weiteren kryptografischen Operationen.

Message 5 + 6 — Authentisierung (ID + Hash)

Die eigenen Identitäten (site-a.mannheim/site-b.heidelberg) werden zusammen mit einem HMAC-Hash über alle bisherigen Nachrichten ausgetauscht. Der Hash beweist die Kenntnis des PSK.

Nach Message 6 steht die IKE-SA — der sichere Kanal für die Kontrollnachrichten. Jetzt folgt Quick Mode (Phase 2), in dem die eigentliche IPSec-SA für den Datenverkehr ausgehandelt wird.

Tunnel-Status und Verifikation

Der Tunnel ist etabliert, wenn ipsec statusall eine ESTABLISHED-IKE-SA und eine INSTALLED-CHILD-SA anzeigt.

TERMINAL ipsec statusall — Tunnel ist etabliert
$ docker exec ipsec-vpn-lab-site-a-1 ipsec statusall ... site-to-site[2]: ESTABLISHED 28 seconds ago site-to-site{2}: INSTALLED, TUNNEL, reqid 1 site-to-site{2}: 10.0.1.0/24 === 10.0.2.0/24 site-to-site{2}: AES_CBC_256/HMAC_SHA2_256_128/MODP_2048

Der Beweis, dass der Datenverkehr wirklich verschlüsselt wird, liegt in den xfrm-Policies des Linux-Kernels:

BASH ip xfrm policy — Traffic Selectors im Kernel
$ docker exec ipsec-vpn-lab-site-a-1 ip xfrm policy src 10.0.1.0/24 dst 10.0.2.0/24 dir out priority 375423 tmpl src 10.255.0.10 dst 10.255.0.20 proto esp spi 0xc712d877 reqid 1 mode tunnel

Der kritische Teil: Die dir out-Policy sagt dem Kernel: „Jedes Paket von 10.0.1.0/24 nach 10.0.2.0/24 muss verschlüsselt werden — bevor es das Interface verlässt." Der spi (Security Parameter Index) verweist auf den SAD-Eintrag mit dem tatsächlichen Session-Key.

Der Ping-Test — beide Richtungen

Das eigentliche Erfolgskriterium: Pakete müssen über den Tunnel laufen. Getestet wird mit ping -I 10.0.1.1, damit die leftsubnet-Policy matcht.

BASH Ping von Site-A (Mannheim) zu Site-B (Heidelberg)
$ docker exec ipsec-vpn-lab-site-a-1 ping -c 4 -I 10.0.1.1 10.0.2.1 PING 10.0.2.1 (10.0.2.1) from 10.0.1.1: 56 data bytes 64 bytes from 10.0.2.1: seq=0 ttl=64 time=0.521 ms 64 bytes from 10.0.2.1: seq=1 ttl=64 time=0.316 ms 64 bytes from 10.0.2.1: seq=2 ttl=64 time=0.354 ms 64 bytes from 10.0.2.1: seq=3 ttl=64 time=0.192 ms -- 10.0.2.1 ping statistics --- 4 packets transmitted, 4 packets received, 0% packet loss

0 % Paketverlust — in beide Richtungen. Die durchschnittliche Latenz liegt bei 0,35 ms (Container-intern). Ein realer Tunnel über das Internet wäre natürlich langsamer, aber die Konfiguration ist identisch.

Dead Peer Detection — was passiert bei Ausfall?

DPD ist in der Konfiguration auf dpdaction=restart gesetzt. Wenn die Gegenstelle 120 Sekunden lang nicht auf DPD-RTT-Abfragen antwortet, wird die IKE-SA gelöscht und StrongSwan versucht einen automatischen Neuaufbau. Im Log sieht das dann so aus:

STRONGSWAN LOG DPD-Timeout und Re-Initiation
07[NET] received packet: from 10.255.0.20[500] 07[IKE] sending DPD request 07[IKE] DPD: peer not responding, deleting IKE_SA 07[IKE] IKE_SA deleted, queueing QUICK_MODE task 07[IKE] initiating Main Mode IKE_SA site-to-site[2]

Wie der Datenpfad funktioniert

Viele Tutorials erklären IPSec nur auf Konfigurationsebene. Hier der tatsächliche Datenfluss durch den Linux-Netzwerkstack:

Ping von 10.0.1.1 → 10.0.2.1 1. Socket schreibt → Quelle 10.0.1.1, Ziel 10.0.2.1 │ 2. Routing-Table → Kein direktes Netz → Default-Route über eth0 │ 3. xfrm Policy (OUT) → Match: src=10.0.1.0/24, dst=10.0.2.0/24 │ → „Verschlüsseln mit SPI 0xc712d877" │ 4. ESP-Verarbeitung → Klartext in AES-256-CBC + HMAC-SHA-256 verpackt │ → Neuer Outer-Header: src=10.255.0.10, dst=10.255.0.20 │ 5. eth0 sendet → ESP-Paket (Protokoll 50) an 10.255.0.20 │ ╔═══════════════════════════════╗ ║ Internet (Docker) ║ ╚═══════════════════════════════╝ │ 6. eth0 empfängt → ESP-Paket, Ziel 10.0.2.1 │ 7. xfrm Policy (IN/FWD) → Match → Entschlüsseln │ 8. Loopback delivery → Klartext an 10.0.2.1 (dev lo)

Was ich gelernt habe

Policy-based vs. Route-based

Policy-based VPNs arbeiten mit xfrm-Regeln direkt im Kernel. Das ist mächtig, aber unflexibel bei komplexen Topologien. Route-based (VTI) ist der logische nächste Schritt.

IKEv1 vs. IKEv2

IKEv1 Main Mode braucht 6 Messages. IKEv2 kommt mit 4 aus (INIT + AUTH) und unterstützt nativ Mobility und Mehrfach-Authentisierung. Für das Labor war IKEv1 aber der richtige Einstieg — die Debug-Ausgaben sind leichter lesbar.

Docker als VPN-Labor

Zwei StrongSwan-Container auf einem MacBook Air — kein Lüfter wurde hörbar. Der Linux-Kernel des Colima-VM erledigt die xfrm-Verarbeitung nativ. Das Setup ist reproduzierbar und versionierbar.

Debugging mit charondebug

StrongSwans charondebug ist der Schlüssel: "ike 1" für Normalbetrieb, "ike 3" für jedes einzelne Paket. Kombiniert mit "knl 2" sieht man jede xfrm-Änderung im Kernel.
