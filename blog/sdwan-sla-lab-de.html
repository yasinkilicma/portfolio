SD-WAN SLA-Path-Selection in Docker
— automatisches WAN-Failover bei SLA-Verletzung

Das Kernprinzip von SD-WAN in einem Docker-Lab: ein Python-Controller auf site-a pingt sekündlich zwei simulierte WAN-Links, entscheidet mit einer reinen, unit-getesteten Policy-Funktion, welcher Pfad aktiv ist, und schaltet eine Host-Route per ip route replace um. Ein tc netem-Skript injiziert künstliche Latenz und Paketverlust, um Failover live zu demonstrieren. Gemessene Erkennungs- und Umschaltzeit: 6-9 Sekunden.

Das Problem, das SD-WAN löst

Eine Zweigstelle hat zwei Internetanschlüsse: einen schnellen Glasfaser-Link (WAN-1) und einen langsameren LTE-Backup (WAN-2). Im Normalbetrieb läuft alles über WAN-1. Fällt WAN-1 aus — Kabelschaden, Provider-Störung — bricht ohne Gegenmaßnahme die Verbindung ab, bis jemand manuell auf den Backup-Anschluss umschaltet.

SD-WAN löst das, indem ein Controller die Link-Qualität kontinuierlich misst und die Route bei einer Schwellwertverletzung automatisch umschaltet, ohne manuellen Eingriff. Dieses Lab baut genau diesen Mechanismus nach: zwei Alpine-Container, zwei isolierte Docker-Netzwerke als WAN-1/WAN-2-Simulation, und ein Python-Controller, der die Entscheidung trifft.

Topologie und Datenfluss

Zwei Alpine-Container, zwei isolierte Docker-Bridges, eine Service-IP auf dem Loopback des Responders. Der Controller auf site-a misst beide Links und hält eine Host-Route 10.100.0.1/32, die er zwischen den zwei Next-Hops hin- und herschaltet.

Container: Site-A (Controller / Branch) Container: Site-B (Responder / Hub) 10.81.0.10 (WAN-1) 10.81.0.20 (WAN-1) 10.82.0.10 (WAN-2) 10.82.0.20 (WAN-2) │ │ │ wan1-net (10.81.0.0/24) ───────────────────────── │ │ wan2-net (10.82.0.0/24) ───────────────────────── │ │ │ │ controller.py: ping → decide → ip route replace │ │ │ Route: 10.100.0.1/32 via 10.81.0.20 (WAN-1, aktiv) 10.100.0.1/32 auf lo

Die Service-IP 10.100.0.1/32 ist an das Loopback-Interface von site-b gebunden und steht stellvertretend für einen Anwendungs-Endpunkt hinter der Zentrale (z. B. eine interne Datenbank). Der Controller schaltet nur die Route zu dieser einen IP zwischen den zwei Next-Hops um, nicht den gesamten Default-Route-Traffic.

Die drei Bausteine des Controllers

1. Entscheidungslogik — sla_policy.py (pure, unit-getestet)

Die Entscheidungslogik ist bewusst I/O-frei gehalten: keine Pings, keine ip route-Aufrufe. Nur Datenklassen und eine decide()-Funktion. Dadurch lässt sie sich in Millisekunden mit pytest testen — ohne Docker, ohne Root.

PYTHON sla_policy.py — Schwellwerte und Hysterese
LATENCY_THRESHOLD_MS = 80.0 LOSS_THRESHOLD_PCT = 5.0 HYSTERESIS_GOOD_COUNT = 3 def link_ok(metrics: LinkMetrics) -> bool: if metrics.latency_ms is None: return False return (metrics.latency_ms <= LATENCY_THRESHOLD_MS and metrics.loss_pct <= LOSS_THRESHOLD_PCT) def decide(state, wan1, wan2) -> str: if state.active_path == "wan1": if link_ok(wan1): return "wan1" return "wan2" if link_ok(wan2) else "wan1" # active_path == "wan2" — Hysterese vor Rückwechsel if link_ok(wan1): state.good_streak_on_primary += 1 if state.good_streak_on_primary >= HYSTERESIS_GOOD_COUNT: return "wan1" return "wan2"

Warum Hysterese? Ohne die "3 gute Messungen"-Regel würde der Controller beim kleinsten Flackern hin- und herspringen — TCP-Verbindungen brechen ständig ab und werden neu aufgebaut, schlimmer als der ursprüngliche Fehler. Hysterese ist Schwingungsdämpfung für Netzwerk-Entscheidungen.

13 Unit-Tests decken alle Edge-Cases ab: beide Links gesund, WAN-1 kaputt, beide kaputt (bleib auf dem aktuellen Pfad statt gegen einen anderen kaputten zu tauschen), Hysterese-Reset bei Relapse, plus eine Regression für einen echten Parsing-Bug (dazu weiter unten mehr). Ergebnis:

2. Probe-Loop — controller.py (ping + route)

Der Controller verbindet die Entscheidungslogik mit dem Kernel. Pro Sekunde: zwei Pings (einer über WAN-1, einer über WAN-2), Parsen der stdout, decide(), und falls der Entscheid vom aktuellen Pfad abweicht: ip route replace mit Zeitstempel loggen.

PYTHON controller.py — Probe-Loop mit Route-Switching
def probe_loop(): state = ControllerState(active_path="wan1") while True: wan1 = run_ping(WAN1_GW) wan2 = run_ping(WAN2_GW) new_path = decide(state, wan1, wan2) if new_path != state.active_path: log(f"SLA violation -> switching {state.active_path} -> {new_path}") apply_route(new_path) # ip route replace 10.100.0.1/32 via <gw> state.active_path = new_path time.sleep(PROBE_INTERVAL_SECONDS)

3. WAN-Degradation — scripts/degrade.sh

Um Failover live zu demonstrieren, braucht es eine kontrollierte Störung. tc netem ist ein Linux-Kernel-Tool, das Traffic gezielt verschlechtert — Latenz, Paketverlust, Jitter. Das Skript ermittelt das WAN-1-Interface zur Laufzeit über die IP-Adresse, statt eth0 hart zu codieren, weil die Interface-Reihenfolge bei einem Container-Neustart nicht garantiert ist.

BASH degrade.sh — künstliche WAN-Degradation an/aus
# WAN-1 verschlechtern: 150ms Latenz + 20% Paketverlust $ ./scripts/degrade.sh on WAN-1 degraded on eth0 (150ms delay, 20% loss) # WAN-1 wiederherstellen $ ./scripts/degrade.sh off WAN-1 restored on eth0

Gemessene Failover-Zeit: 6-9 Sekunden (über mehrere Läufe) — vom degrade.sh on-Zeitpunkt bis zum switching wan1 -> wan2-Zeitstempel im Log. Die Spanne kommt vom Ping-Timeout-Zyklus (bis zu 3×1s pro Link und Runde).

Der Entscheidungsbaum

LOGIK decide() in Worten, Schwellwertlogik ohne Kommentare
# Auf WAN-1: if wan1 ok: → bleib auf wan1 else if wan2 ok: → wechsle zu wan2 else: → bleib auf wan1 (aktuellen Pfad nicht gegen einen anderen kaputten tauschen) # Auf WAN-2: if wan1 ok: streak += 1 if streak >= 3: → wechsle zurück zu wan1, streak=0 else: → bleib auf wan2 (noch nicht genug Beweise) else: → streak=0, bleib auf wan2

Schwellwerte und ein Zähler reichen für den Kern der SLA-basierten Pfadselektion — kommerzielle SD-WAN-Appliances bauen im Kern auf demselben Prinzip auf, meist erweitert um mehr Metriken (Jitter, Bandbreite) und mehr als zwei Pfade.

Was ich gelernt habe

TDD lohnt sich

Die 13 Unit-Tests haben zwei Denkfehler im Entscheidungsbaum aufgedeckt, bevor ich eine Zeile Controller-Code geschrieben habe. Der Test "beide kaputt → bleib auf WAN-1" war der wichtigste.

Hysterese ist nicht optional

Ohne "3 gute Messungen"-Regel würde der Controller beim kleinsten Flackern ping-pong-spielen. Hysterese ist Schwingungsdämpfung — in echten Netzwerken genauso wichtig wie im Lab.

tc netem statt echter Störung

Kein kaputter Internetanschluss nötig, um Failover zu testen. Ein Befehl simuliert jede WAN-Pathologie — Latenz, Jitter, Loss, Bandbreiten-Limit — reproduzierbar und ohne Seiteneffekte auf andere Verbindungen.

Kein dev-Iface-Hardcoding

Der Kernel löst das ausgehende Interface aus der Connected-Subnet-Route zum Gateway automatisch. ip route ... via 10.81.0.20 ohne dev eth0 — nie wieder Interface-Reihenfolge raten.

Handgeschriebene Testdaten reichen nicht

Live-Log zeigte einen unmöglichen Wert: loss_pct=6667.0. Ursache: Alpines ping schreibt Verlust bei nicht-runden Quoten mit Nachkommastellen (66.6667%), meine Regex (\d+)% packet loss erwartete nur Ganzzahlen und griff sich die Ziffern hinter dem Komma. Die Entscheidung war trotzdem richtig (Schwellwert längst überschritten), aber die Metrik war Unsinn. Meine Tests hatten nie das reale Format genutzt — daher Test 13.

Nächste Schritte

Dieses Lab deckt bewusst nur einen Aspekt von SD-WAN ab: die SLA-basierte Pfadselektion. Was noch fehlt — und anhand der Vorgängerprojekte ipsec-vpn-lab und ipsec-vpn-ikev2 direkt weitergeht:

Als Nächstes: ADVPN Hub-Spoke (3+ Sites, dynamische Shortcut-Tunnel), BGP over VTI (richtiges dynamisches Routing statt einer statischen Host-Route), und die Kombination mit IPSec — dann hat man genau das, was kommerzielle SD-WAN-Produkte machen.
