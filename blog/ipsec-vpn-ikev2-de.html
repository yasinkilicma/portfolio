IKEv2 Route-based VPN mit XFRM-VTI in Docker
— Migration von Policy-based zu Route-based

Nach dem Policy-based-IKEv1-Lab war der logische nächste Schritt: IKEv2 mit einem XFRM-Virtual-Tunnel-Interface. Dieses Projekt baut auf dem Vorgänger auf, ersetzt das Protokoll und führt ein virtuelles Tunnel-Interface ein. Der Unterschied: Policy-based matcht Subnetz-Paare im Kernel – Route-based lenkt Traffic per Route in ein Interface und verschlüsselt alles, was es durchquert. Flexibler, erweiterbarer und die Basis für ADVPN und SD-WAN.

Warum Route-based?

Das erste Labor hat gezeigt, wie ein Policy-based-VPN funktioniert: StrongSwan installiert xfrm-Policies im Kernel, die genau definieren, welche Subnetz-Paare verschlüsselt werden. Sobald man aber ein neues Subnetz hinzufügt oder eine komplexere Topologie aufbaut (Hub-Spoke, dynamische Routen), wird dieser Ansatz unflexibel.

Ein Route-based-VPN entkoppelt Routing und Verschlüsselung. Der Tunnel bekommt ein eigenes virtuelles Interface (hier: xfrm0), das eine IP-Adresse aus einem Tunnel-Netz trägt. Statt Subnetz-Paaren definiert die xfrm-Policy nur noch: „Alles, was dieses Interface verlässt, wird verschlüsselt". Die Steuerung, welcher Traffic den Tunnel nimmt, liegt in der Routingtabelle – nicht im IPSec-Config.

Der entscheidende Unterschied: Policy-based = „Verschlüssele alles von 10.0.1.0/24 nach 10.0.2.0/24". Route-based = „Verschlüssele alles, was durch Interface xfrm0 geht". Ein neues Subnetz? Einfach eine Route hinzufügen – kein IPSec-Config-Change.

Topologie und Datenfluss

Die IP-Adressen und Docker-Netze sind gegenüber dem Vorgänger unverändert, das Tunnel-Netz 10.99.0.0/30 kommt neu hinzu.

Der Datenpfad im Detail

Wenn Site-A ein Paket an Site-Bs LAN (10.0.2.1) sendet, durchläuft es diesen Weg:

Paket: src=10.0.1.1, dst=10.0.2.1 1. Routing-Table → Match: 10.0.2.0/24 dev xfrm0 │ 2. xfrm0-Interface → Interface if_id=42, Paket wird „VTI-intern" │ 3. xfrm Policy (OUT) → Interface-Match → ESP-Verschlüsselung mit SPI │ → Neuer Outer-Header: 10.255.1.10 → 10.255.1.20 │ 4. eth0 sendet → ESP-Paket (Protokoll 50) über das Docker-Netz │ 5. Site-B eth0 empfängt → Entschlüsselung via xfrm Policy (IN/FWD) │ 6. xfrm0 → Klartext-Paket erscheint auf xfrm0 (if_id=42) │ 7. Routing → 10.0.2.1 → Zustellung via Loopback

Die Konfiguration — was sich geändert hat

ipsec.conf – IKEv2 + if_id

Die wichtigsten Änderungen gegenüber dem IKEv1-Projekt: keyexchange=ikev2, die Traffic-Selectors enthalten jetzt auch das Tunnel-Netz, und if_id=42 bindet die SA an das xfrm-Interface.

IPSEC.CONF Site-A – IKEv2 + XFRM-VTI (Auszug)
conn site-to-site-vti auto=start keyexchange=ikev2 authby=secret # Site-A (Mannheim) left=10.255.1.10 leftid=@site-a.mannheim leftsubnet=10.0.1.0/24,10.99.0.1/32 # Site-B (Heidelberg) right=10.255.1.20 rightid=@site-b.heidelberg rightsubnet=10.0.2.0/24,10.99.0.2/32 # XFRM-Interface-Bindung if_id=42 # Krypto wie gehabt ike=aes256-sha256-modp2048! esp=aes256-sha256-modp2048!

ipsec.secrets – Wildcard-PSK

IKEv2 authentisiert nicht mehr über IP-Paare, sondern über die IKE-IDs (@site-a.mannheim). Das Secrets-Format verwendet daher einen Wildcard-Eintrag, der für alle Peers gilt.

IPSEC.SECRETS Wildcard-PSK – gilt für jede ID
: PSK "Mannheim-Heidelberg-2024-Gizli-Anahtar"

entrypoint.sh – VTI-Interface erstellen

Das Skript erstellt das xfrm0-Interface und die Route zum remote LAN – alles über Umgebungsvariablen aus der docker-compose.yml.

BASH entrypoint.sh – VTI-Setup (Auszug)
ip link add xfrm0 type xfrm dev eth0 if_id 42 ip addr add 10.99.0.1/30 dev xfrm0 ip link set xfrm0 up ip route add 10.0.2.0/24 dev xfrm0

Das xfrm-Interface: Anders als ein klassisches VTI benötigt das XFRM-Interface (type xfrm) kein eigenes Tunnel-Modul mehr – es ist direkt in den Linux-Kernel integriert. Die if_id muss mit dem Wert in ipsec.conf übereinstimmen.

Verifikation – Tunnel und Datenpfad

IKEv2-Aushandlung (4 Messages)

IKEv2 kommt mit zwei Roundtrips aus: IKE_SA_INIT (DH-Key-Exchange + Nonces) und IKE_AUTH (ID + PSK-Authentisierung + erster CHILD_SA). Der Log-Ausschnitt zeigt den kompletten Ablauf.

Policy-based vs. Route-based – der direkte Vergleich

Beide Labore (Proje 1 und Proje 2) liegen jetzt als getrennte Projekte vor. Die Unterschiede lassen sich direkt an den Konfigurationen ablesen.

PROJE 1 / PROJE 2 Die zwei xfrm-Ansätze im Kernel
# Policy-based (Proje 1): Kernel matcht Subnetz-Paare src 10.0.1.0/24 dst 10.0.2.0/24 dir out → Verschlüsseln # Route-based (Proje 2): Kernel matcht Interface + if_id Paket verlässt xfrm0 (if_id=42) → Verschlüsseln (egal welche src/dst)

Wann nehme ich was? Policy-based ist einfacher für statische Site-to-Site-Verbindungen mit wenigen Subnetzen. Route-based wird ab drei oder mehr Standorten und dynamischem Routing (BGP/OSPF über den Tunnel) zwingend notwendig – und ist die Architektur, die Fortinet mit ADVPN und SD-WAN umsetzt.

Was ich gelernt habe

IKEv2 ist schlanker

Vier statt sechs Nachrichten. Kein Aggressive Mode nötig. NAT-T und MOBIKE sind nativ integriert. Die Aushandlung ist robuster bei wechselnden IPs.

PSK-Lookup in IKEv2

IKEv2 authentisiert über die IKE-ID (@site-a.mannheim), nicht über die Quell-IP. Das Secrets-Format musste von IP IP : PSK auf Wildcard : PSK geändert werden.

Das xfrm-Interface

Der Linux-Kernel unterstützt XFRM-Interfaces nativ (kein Kernel-Modul nötig). Die if_id-Bindung ist eleganter als das alte VTI-Modell.

Ein Projekt, zwei Zweige

Durch die Trennung in zwei getrennte Docker-Compose-Projekte mit unterschiedlichen Netzwerken (10.255.0.0/24 vs. 10.255.1.0/24) können beide Parallel laufen – ideal für den direkten Vergleich.
